# Form validation and temporary drafts

Last reviewed: 2026-10-15.

`lib/form-fields.ts` is the shared validation boundary for native form answers. `validateFormResponses` rejects unknown keys and nested/non-scalar values, enforces field-specific string limits, validates email and real ISO calendar dates, restricts dropdown values to configured options, accepts only boolean checkbox answers, and normalizes finite numeric answers within JavaScript's safe range. Only visible required fields require answers. Hidden answers still need valid types and values when supplied, but do not affect risk scoring or overwrite conditionally hidden client identity fields. Empty identity answers preserve existing client details. Template normalization excludes duplicate and prototype-sensitive keys.

`POST /api/forms/[id]/submit` authenticates, checks client access and open engagement context, then accepts a bounded JSON request. It validates new answers, merges them with previously saved answers so omitted values survive, checks all required answers, and calculates native risk on the server. `DataStore.submitFormOnce` repeats validation against the current snapshot and conditionally accepts only `not_started` forms inside the versioned mutation. The same commit updates form status/answers, synchronizes client identity, appends activity, and queues matching webhook delivery intents. Concurrent losers return 409 without overwriting evidence or duplicating events. Delivery remains asynchronous through the durable queue. A caller's `riskScore` is ignored. Google Forms retain their external collection flow and stored responses; native answer payloads cannot be injected into a Google form without a schema. The client portal uses the same validator and labels individual field errors; closed engagement forms are read-only.

`lib/session-drafts.ts` stores versioned drafts in sessionStorage only. Portal draft keys include the authenticated user, client, engagement (or account-wide context), form, and template. The field-schema fingerprint prevents restoring an incompatible draft after a template changes. Intake drafts are scoped to the authenticated staff user; removed staff/playbook selections are reset on restoration. Unfinished invalid text survives refresh so the user can correct it. Drafts expire after 24 hours since the last change, are cleared when browser authentication ends or changes user, and are removed after successful submission/creation or explicit discard. Portal closing preserves the draft, and explicit discard asks before clearing answers. Page unload warns about unfinished answers; intake Cancel also asks before leaving.

Draft feedback distinguishes sessionStorage success from unavailable/full browser storage. If storage fails, the portal keeps draft answers in page memory for close/reopen and says that refresh/navigation can lose them. Drafts are never reported as submitted and are not sent to staff until the submission succeeds. This is temporary tab-local storage, not an encrypted or durable cross-device draft service. Closing the tab, browser policy, sign-out, or expiration can remove drafts. No new database model or server draft endpoint is added.

Focused tests cover invalid email/dropdown values, unexpected shapes and keys, number/date boundaries, conditional required/risk behavior, identity preservation, scoped draft isolation, expiration/malformed data, cleanup, and browser-storage failure. Production authenticated submission and browser-device verification require the normal staging workflow.

The isolated HTTP suite verified malformed submissions, a single winning concurrent native submission with one activity/webhook intent, capability revocation, task-inherited context, and closed-context rejection. Local mobile browser verification restored answers after closing/reopening and successfully submitted a synthetic native brief; intake invalid email remained on its brief step. These local checks do not establish hosted provider or device behavior.

## Work context in forms and messages

Portal Forms and the staff/client Messages pages accept an `engagementId` query parameter and provide a labeled work-context selector. The default All work view preserves the existing account-level list. `engagementId=account` selects resources explicitly scoped to the account, and a specific engagement selects that engagement. A separate checkbox deliberately includes account-wide resources (`includeAccountWide=1` or `true`); its default is off. Each form/message displays its context. An engagement link can open the appropriate filtered surface without silently mixing in other engagements.

Forms GET validates a requested engagement against the owning client, permits closed engagements for historical reads, and enriches old task-linked forms with inherited context. Unlinked historical forms remain account-wide. Hodi `assign_form` checks engagement ownership/status when the proposal is previewed and again at execution, then puts the created task and form in that engagement. Its existing task-creating flow defaults to the legacy onboarding engagement; `/forms` still manages reusable templates rather than assignments.

Message composition names its sending destination. In All work or Account-wide views, new messages remain account-wide; selecting an engagement attaches its ID. Completed/cancelled engagements are read-only for message creation. Changing staff clients clears unsent message text after a warning, avoiding accidental reuse in another client's conversation. Message length is limited to 10,000 characters in the UI; authorization and validation remain server responsibilities.

`useMessageRealtime` still subscribes to the authorized client-level room, then filters frames through the pure `messageMatchesContext` helper. Reconnecting for a context/user change cannot report the prior subscription as connected. Keyed page state and request generations prevent old HTTP results from appearing under a newly selected client/context. `useMessagePolling` resets its refresh loop when the thread key changes and remains the fallback while the socket is unavailable. The UI describes the connection state rather than promising live connectivity during polling. These context labels do not change client-level access boundaries.
