# Client OS architecture record

Last reviewed: 2026-10-15. This records repository behavior and boundaries; deployment state is in [status.md](status.md). The September account/task split is deployed. The additional resource scoping and audit remediation below are current working-tree changes and have not been released by this work.

## Account and engagement

The existing `Client` in `StoreSnapshot` remains the account identity and retains its ID, primary contact, assigned team member, portal users, tags, and historical records. Its `status` and `pipelineStage` still describe the original onboarding workflow for compatibility. They are labeled as legacy onboarding controls in the staff workspace.

`Engagement` is a relational record for a bounded onboarding, project, or ongoing service under one client. It stores name, type, status (`planned`, `active`, `paused`, `completed`, `cancelled`), owner, dates, and completion time. A client can have multiple engagements. Work tasks remain in `StoreSnapshot`; new tasks carry `engagementId`. Old tasks without it resolve to `onboarding_<clientId>`. Progress is computed from tasks in that engagement, not all client tasks.

The October fix preserves explicit task engagement IDs during snapshot normalization. Previously, normalization could drop them on a later mutation, which also misplaced task-linked forms. Existing records already missing an ID still use the legacy fallback; this change does not guess or recover an earlier intended assignment.

The additive migration `20260927000000_add_client_engagements` creates `Engagement` and `ClientContact`, then backfills one stable legacy onboarding engagement and primary directory contact per existing client. New client creation ensures those rows. The migration does not rewrite old task IDs or snapshot data. It was applied in the September release recorded in [status.md](status.md); a fresh environment must apply it before serving routes that query either table.

Historical onboarding completion time is approximated from the last client update because the old client record has no dedicated completion timestamp. Dashboard and analytics label the resulting duration accordingly.

## Routes and access

- `GET/POST /api/clients/[id]/engagements` lists or creates engagements. `GET/PATCH /api/engagements/[id]` reads or changes one. Client users may read their own engagements; staff may create/change only for currently assigned clients (admins can access all).
- `GET /api/tasks?clientId=...&engagementId=...` filters tasks to an engagement; client users still receive only client-facing tasks. Task creation accepts a same-client `engagementId`. Closed engagement task workflow mutations are rejected; historical comments remain available.
- `GET/POST /api/clients/[id]/contacts` and `PATCH/DELETE /api/clients/[id]/contacts/[contactId]` manage a contact directory. Only authorized staff mutate it. Directory roles describe contact responsibility; they do **not** grant portal login or change API permissions. Portal access still comes from a client user account with `UserProfile.clientId` and existing invitation flow.
- Staff account and client portal pages list engagements and show work in engagement context. The portal engagement view retrieves tasks, milestones, approvals, documents and forms in parallel and links to filtered resource pages. Account-wide items remain explicitly available alongside engagement work.
- Form/document reads accept optional `engagementId`; absent means all client work, `account` means account-wide only, and a real ID selects that engagement. `includeAccountWide=1` deliberately includes account resources beside the selected engagement. Staff/client message views use the same context selection. These filters narrow an already authorized client view; they do not grant access to another client's engagement.
- Native form submission and review, document upload/review/metadata changes, new messages, milestone/approval creation and approval decisions reject completed/cancelled engagement context. Historical reads remain available. Document bulk review authorizes and validates the entire selection before changing any target.

## Resource context and persistence

Tasks retain their required resolved engagement: an old task without `engagementId` still belongs to `onboarding_<clientId>`. Forms, documents, messages, milestones and client approval requests now have optional engagement context. `lib/resource-engagement-scope.ts` resolves a form/document's explicit engagement first, then its same-client linked task, otherwise account-wide. Existing unlinked records remain account-wide; there is no blanket reassignment to onboarding. New linked form/upload routes inherit the task's engagement and reject mismatched client/task/engagement references through `lib/engagement-resources.ts`.

Document metadata and version references remain in `StoreSnapshot`, while current/historical bytes move into Neon `DocumentContent` through `20261014000000_separate_document_content_and_integration_jobs`. JSON list, detail and mutation endpoints return metadata only. `GET /api/documents/[id]/content` authorizes the owning client and retrieves current or indexed historical content bound to that document/client. It supports private preview/download and byte ranges. The new upload path validates content and records replacement history against the current snapshot; replacements preserve classification/expiry and reset review status. Legacy metadata-only POST writes and file replacement through PATCH are rejected so they cannot bypass that path.

Native forms share field rules between the portal and server. `DataStore.submitFormOnce` validates the current form/template, merges omitted stored answers, calculates risk, prevents duplicate or reviewed-state overwrites, updates client identity, appends activity and enqueues webhook intent in one conditional snapshot write. Hidden/empty identity answers do not erase existing client details. Google Forms retain external collection and separate marking/review behavior. Portal and staff intake drafts use scoped sessionStorage with a 24-hour lifetime, honest storage-failure feedback, authentication cleanup and explicit discard warnings; they do not create durable server drafts.

Messages carry optional engagement IDs, and notification links preserve the destination context. All-work and Account-wide views send account-wide messages; a selected engagement sends into that engagement. Closed or unavailable engagements cannot receive new messages. The realtime room remains client-scoped, with context filtering in the hook and keyed HTTP/polling state to prevent messages from an old conversation appearing after a context change. This keeps the existing client-level authorization model.

Hodi form assignments validate engagement ownership/status during preview and execution, then create their linked task/form in that engagement. Both Project operations and Hodi milestone/approval creation accept optional engagement context and check same-client ownership/open status. A linked milestone infers its first task's engagement when omitted, including the deterministic legacy onboarding fallback; every additional task must belong to that same engagement. Truly unlinked work without an engagement remains account-wide. Proposal previews name the selected engagement, and execution repeats current validation before persisting the context. The shared template editor remains account-independent; templates are assigned through tasks or Hodi rather than belonging to one client engagement.

## Current boundaries

The snapshot remains the source of truth for tasks, forms, document metadata, messages and project operations. Separating document bytes reduces snapshot size but does not make the remaining arrays relational. Calendar schedules, delivery health, legacy onboarding automation and some reports/exports remain account-level; an engagement filter must not imply those models are engagement-scoped. MCP project authorization remains client-based, with engagement context carried by the records it returns where available. The current account owner is still one assigned team member, and a portal user still belongs to one client account. Contact directory roles are not authorization roles.

Current database-backed session resolution enforces staff capability rules alongside role and assignment checks. Admins retain all capabilities. For team users, an omitted permission list selects defaults, while explicit `[]` grants no staff capabilities. File replacement/client editing requires `clients.manage`; document/form review uses its respective review grant. Shared controls expose proper labels/selection state and comfortable touch targets, and restricted UI hides or disables mutations without relying on the UI for authorization. See [permissions.md](permissions.md) and [interface-audit-remediation.md](interface-audit-remediation.md).

The existing onboarding health and completion automation use only legacy onboarding tasks. Dashboard and analytics report active engagement counts from relational rows. A future move of other high-volume work out of `StoreSnapshot` should be driven by measured read/write load and a separate migration, not by this account split alone.

Shared portal, staff, marketing, and mail copy describes the client account, workspace, engagements, and delivery work. The word “onboarding” remains for the onboarding engagement, its legacy status/health/reporting, and its dedicated completion and nudge automation. Internal route names, stable IDs, event names, and template types retain their existing values for compatibility. Transactional mail uses a provider-verified general sender address with a message-specific Boatship display name; it does not impersonate the assigned staff member. Client and team invitations use separate bodies. Task assignment wording follows its engagement, while account-wide documents, security mail, and digests use general Client OS language.

File-only local demo mode synthesizes the legacy onboarding engagement and primary contact so existing pages and tasks still load. Creating additional engagements or contacts in that mode returns 501; those writes require the relational database. It can keep binary files and integration jobs locally, while hosted audit-remediation code requires the new relational migration. Real provider actions, production migration and release checks remain environment-dependent and are tracked separately in [status.md](status.md).
