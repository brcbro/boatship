## External action boundaries

- Hodi automation rules persist their enabled state, but the web process does not schedule them. Current runs are initiated explicitly and save review results; they do not send external messages (`lib/hodi-automations.ts`).
- Production enqueues start a webhook or integration-job drain after the response is sent; the Worker cron retries hourly and schedules product overdue notifications when `BOATSHIP_CRON_SECRET` is configured. A failed webhook can be delivered more than once; receivers should deduplicate by `X-Boatship-Delivery`. Most domain writes and webhook enqueue remain separate snapshot mutations; native form submission now queues its webhook intent in the same conditional mutation.
- Integration jobs persist intent before the initiating response returns, but their relational enqueue is separate from domain snapshot writes. Delivery is at least once: a timed-out Slack call can repeat, while Drive/HubSpot lookup mitigates uncertain creation. Missing connections are visible skipped jobs, not successful deliveries. [integration-jobs.md](integration-jobs.md) records provider and scheduler boundaries.
- Hodi communication approval records a handoff-ready draft; direct delivery requires a verified channel contract (`prisma/schema.prisma`, `lib/hodi-communications.ts`).
- Composio, ZeptoMail or Resend, LLM, Redis, and Drive behavior depends on valid configuration and connected accounts. Missing optional services should be understood from route responses and feature code, not inferred from the presence of UI alone.
- Hodi's action catalog is finite: it cannot create arbitrary records. Native form templates and service templates require an admin; client-scoped actions enforce current assignment; Google Calendar creation requires that user's connected account. A multi-step request is handled as separate proposals, with later steps using IDs returned from earlier executions.
- Product payment/customer/analytics integrations and product-specific Git validation are deferred; [product plan](../docs/products-saas-integration-plan.md) gives the intended boundaries.

## Current audit release requirements

`20261014000000_separate_document_content_and_integration_jobs` creates the binary-content and integration-queue tables and moves existing current/version base64 content into separate Neon records before removing it from snapshot JSON. Apply this migration before serving the new upload/queue code. File-only demo mode retains local binary files and its durable local queue; it does not establish hosted behavior.

[forms-validation-drafts.md](forms-validation-drafts.md), [interface-audit-remediation.md](interface-audit-remediation.md), and [permissions.md](permissions.md) give the exact temporary-draft, accessibility, navigation and capability rules. Drafts are tab-local, expire after 24 hours since their last change, and clear on authentication changes; they are not a server or cross-device draft service. Production authentication, provider delivery and migration/deployment evidence belong in [status.md](status.md), not in the presence of these UI controls.
