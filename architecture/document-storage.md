# Document content and runtime scaling

Last reviewed: 2026-10-23. Implemented in the working tree; not yet deployed.

## Where bytes live now

Since 2026-10-23 file bytes are stored in the PostgreSQL database beside the documents ([postgres-store.md](postgres-store.md)): `PostgresFirestore` keeps a `documents_blobs` table (`key text primary key, bytes bytea, content_type, size, created_at`), and `lib/document-objects.ts` returns that table as the `DocumentObjectStore` whenever the database is PostgreSQL, ahead of Firebase Storage. Firebase Storage is used only when the Firestore fallback is the database and `FIREBASE_STORAGE_BUCKET` is set; with neither, small files stay inline. The `DocumentContent` record and the `objectKey` layout (`documents/<clientId>/<documentId>/<contentId>`) are unchanged, so save, read, cleanup, cascade deletion, and the backfill route work the same against either store. The upload limit is 25 MiB (`DOCUMENT_MAX_BYTES`), raised from 10 MiB; a file travels as base64 JSON through the Worker and is written in one `INSERT` on a bytea column, which is reasonable for documents up to that size and not intended for video. `npm run test:postgres` covers blob put, replace, get, and delete on the live service; `npm run test:e2e:postgres` uploads through the API into a scratch blob table. The description below of Firebase Storage remains accurate for the fallback path.


## File content and metadata

`DocumentContent` is the ownership record for every file: document/client ownership, type, size, and creation time. Its bytes live in one of two places, enforced by a check constraint: the `bytes` column (the original Neon design, still the behavior wherever no object store is bound) or Firebase Storage under `objectKey` when `FIREBASE_STORAGE_BUCKET` and `FIREBASE_SERVICE_ACCOUNT` are set. `lib/document-objects.ts` builds keys as `documents/<clientId>/<documentId>/<contentId>`; `lib/firebase-storage.ts` signs an RS256 service-account assertion with WebCrypto, exchanges it for a cached one-hour access token, and uses the Google Cloud Storage JSON API with fetch, so it runs in the Worker without the Firebase Admin SDK; `lib/document-content.ts` decides per write and resolves per read, always after the database ownership check. There is no public object URL. This is the first step of a possible Cloudflare D1 move, whose 2 MB row limit cannot hold 10 MiB uploads, but it ships on Neon unchanged. `StoreSnapshot.documents` retains current metadata, review/classification/expiry, task/engagement context, and ordered historical metadata containing internal content references. All document JSON responses strip current/history base64 and content IDs; they expose `contentAvailable` to support the viewer. The repository `storage.rules` file governs only client SDK access and does not apply to these server-side writes.

`POST /api/documents/upload` accepts the existing JSON/base64 upload contract. `lib/document-files.ts` validates a 10 MiB byte limit, bounded filename, strict encoding, reported size, and matching PDF/PNG/JPEG/WebP extension, MIME, and signature. Authorization checks own client or current staff assignment/capability, task visibility, existing document ownership, and an open same-client engagement. The route saves bytes, then `persistDocumentUpload` updates metadata/activity inside the retrying snapshot mutation. Competing replacements append the current committed file; a newer classification, expiry, and context survive the retry. Replacement resets current review to pending.

With Firebase Storage configured, a save writes the object first and then the row; a failed row insert deletes the object. File save and metadata commit are separate operations. Cleanup after a failed metadata commit first checks fresh current/history references so an uncertain successful commit cannot delete its file. A process crash before metadata commit can leave an orphan; a periodic orphan/retention process is not implemented. Existing missing file references are reported as unavailable and permit replacement. The local demo stores new content at `.data/document-content/<UUID>.bin`; old local base64 records remain readable. Hosted files stay in Neon until the backfill moves them: `POST /api/internal/document-content-migrate?limit=5`, protected by `BOATSHIP_CRON_SECRET`, copies up to twenty row-stored files per call into Firebase Storage and clears their bytes only after the object write succeeded, returning `moved` and `remaining`. It is idempotent and operator-run, not scheduled. Reads of an object-backed row return unavailable if the secrets are missing, so never remove them while `objectKey` rows exist. Client cascade deletion collects the client's object keys, deletes the rows, then best-effort deletes the objects; a crash between those leaves orphan objects rather than dangling rows.

`GET /api/documents/[id]/content` authenticates before reading the ownership-bound byte row. No `version` selects current; `version=0` selects the first history entry. Invalid indexes return 400, missing bytes 404, and unauthorized access 401/403. Responses set private/no-store, nosniff, sandbox policy, safe encoded filename, and verified MIME. Unknown legacy signatures download as octet-stream. One bounded byte range returns 206; unsatisfiable/malformed ranges return 416. The entire byte record is currently read before slicing, so ranges improve transport rather than database memory usage.

`GET /api/documents/[id]` returns metadata. The former metadata-only document POST and PATCH file replacement are rejected with instructions to use uploads. This closes a bypass that could replace references without validated bytes. PATCH remains staff review/classification/expiry; bulk review prevalidates every selected client's authorization and open context before writing. Multi-document review is still separate snapshot commits after prevalidation, rather than one all-or-nothing batch. Client cascade deletion removes relational byte/job rows with the other relational client data after snapshot removal; that existing cross-store cleanup remains separate from the snapshot commit.

The signature checks do not scan malware or fully parse a PDF/image. Malware scanning, retention policy, backup restoration, and complete privacy deletion verification remain separate operational work.

## Migration and release order

`20261022000000_document_content_object_keys` makes `bytes` nullable, adds `objectKey`, the exclusive-storage check constraint, and an index. It is additive and safe with the previous Worker, which never writes `objectKey`. Release order: create the Firebase project bucket and a service account with Storage Object Admin, set both Worker secrets, apply the migration, deploy, then run the backfill in batches until `remaining` is zero. Rolling back the Worker before the backfill is safe; after it, old code cannot read object-backed rows.

`20261014000000_separate_document_content_and_integration_jobs` creates `DocumentContent` and `IntegrationJob`, then copies current and every historical legacy base64 into BYTEA, replaces each inline payload with a deterministic content reference, preserves metadata order, and advances snapshot version. An explicit PostgreSQL transaction and snapshot table lock keep the copy/reference rewrite atomic. Invalid legacy base64 stops and rolls back the migration instead of discarding content.

Verify a recoverable restore point, quiesce legacy writers, apply the migration, then deploy this code. An old application can write inline content again after the lock is released, so writer coordination is required during rollout. The isolated QA fixture executes the real migration against synthetic current/history files; it never reads hosted credentials or customer files. No migration was executed against production here.

## Request scope and application runtimes

`lib/store-context.ts` limits snapshot reuse to an AsyncLocalStorage request scope. `handleApi` and binary retrieval wrap that scope; callers outside it get a fresh `PrismaStore`. Production no longer uses a process-global delivery-store cache. Every mutation reloads current state and uses the existing version check/retry, so separate runtime instances preserve competing writes.

`lib/runtime-routing.ts` hashes a bounded session identifier or anonymous route key into four `app-0`…`app-3` Durable Object names. A session stays on one instance across routes; raw tokens are never used as names. The existing `APP_RUNTIME` binding and class migration suffice. Four instances remove the former single-instance ceiling, but snapshot contention, optional Redis TTL, and each instance's capacity still need a hosted load test. No throughput or latency claim is made from a local build.

The local loopback PostgreSQL adapter shares one Prisma client and a bounded eight-connection Node transport pool, avoiding idle pools and accumulated adapter listeners during tests. Neon HTTP and hosted Hyperdrive retain request-bound client construction.
