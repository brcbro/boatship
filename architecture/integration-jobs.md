# Durable integration jobs

Last reviewed: 2026-10-14. Hosted execution requires the database migration, configured connections, and the Worker scheduler; this record describes code behavior.

## Persistence and events

`IntegrationJob` is a relational PostgreSQL queue added by the audit-remediation migration. It stores a stable ID / unique dedup key, client ID, original staff actor, provider job kind, minimal event payload, status, attempts, next attempt time, lease token / expiry, safe error and confirmation metadata, and timestamps. It has status/time, client/time, and actor/time indexes. Job intent does not enlarge `StoreSnapshot`.

`lib/integration-jobs.ts` awaits insertion before a client creation, invitation, or task-completion response returns. Creating a client atomically inserts sibling Slack-update and Drive-folder jobs in one SQL statement. An invitation inserts separate Slack and HubSpot jobs. Task completion and legacy onboarding completion insert a Slack job. Client task events resolve the current assigned staff member as the integration actor; an original staff action retains that actor. Execution later rechecks this actor's role, reset state, `clients.manage` capability, and current committed client assignment. Missing clients or revoked authority stop the job with a safe terminal error; a manual retry does not change the actor or grant new authority.

The dedup key is a hash of the persisted event identity plus provider kind. Client creation uses the stable client ID; invitation uses its activity ID; task completion uses task ID and stored completion time; onboarding completion uses a stable hash of legacy onboarding task completion markers. Repeating the same task-completion request repairs a previously missing enqueue without repeating completed provider jobs. Separate providers prevent a failed HubSpot attempt from resending a Slack update that already finished.

Domain snapshot writes, invitation email sending, and integration enqueue are separate operations. A process crash between a domain write and enqueue can still omit intent, and an enqueue failure can occur after the domain record exists. This is a durable queue rather than a transactional domain outbox. The existing direct email and manual reminder flows are not moved into this queue. Product integration work remains separate. All former detached `notifyIntegrations` and Drive provisioning promises in the core client/create/invite/task/status paths are removed.

## Claiming, retry, and recovery

The hosted queue uses parameterized single-statement PostgreSQL CTEs, compatible with the Neon HTTP adapter's lack of interactive transactions. `FOR UPDATE SKIP LOCKED` selects a bounded batch and the update increments attempts and assigns a new random lease token with a five-minute expiry. Concurrent drains receive disjoint jobs. A process interruption makes a processing job eligible after lease expiry. Completion checks the current token before saving results, so an old worker cannot overwrite a reclaimed job.

All new job dates use `TIMESTAMPTZ(3)`. Leases and retry delays are scheduled from database `NOW()` so session timezone and worker clock differences cannot make a future lease immediately eligible. The isolated PostgreSQL fixture exercises a non-UTC session; it does not mask timezone behavior by forcing UTC.

Drains claim ten jobs by default, run their providers independently, and bound a provider attempt to 45 seconds. A thrown/negative/unconfirmed provider result schedules a retry after an exponentially increasing delay, capped at one hour. Ten attempts stop automatic retries. An interrupted final attempt also becomes a terminal failure when its expired lease is recovered. A manual retry of a failed or skipped job starts a new attempt cycle while preserving its ID and dedup key. Completed or currently processing jobs cannot be manually retried.

Missing Composio configuration, an absent connected account, or an absent Slack destination becomes `skipped` with an actionable safe reason, rather than a claimed success. The administrator can configure the connection and retry. Provider response bodies and credential-bearing error text are never copied into queue API responses or stored as job results; results contain only confirmation/provider metadata or a Drive folder ID/link. Failure logs identify the job, kind, and attempt without dumping provider payloads.

For explicit file-only demo mode (`ALLOW_LOCAL_STORE=1` and no `DATABASE_URL`), `LocalIntegrationJobs` persists to `.data/integration-jobs.json`. It serializes operations under a process-local mutex per file, fsyncs a temporary file, and atomically renames it into place. Recreating the store preserves jobs and dedup state. This local queue supports one Node process; concurrent independent Node processes must use the relational database. Corrupt file data fails visibly rather than resetting the queue.

## Provider confirmation and idempotency

`integrationProviderConfirmed` requires Composio's explicit successful wrapper and rejects provider-level negative/error fields, including JSON-encoded bodies. HubSpot jobs search by exact email before creating a contact; retries update the same contact and a failed/uncertain create searches again. Drive jobs first reuse the saved folder ID; otherwise they search for a folder using the stable account ID in its name, within the configured parent or Drive root, before creating it. Confirmed folder metadata is persisted on the client. Existing saved folder IDs are preserved.

Current Composio tool contracts were checked against the official toolkit documentation. Queued/manual Slack tests use `SLACK_SEND_MESSAGE` with `markdown_text`; Drive searches use `GOOGLEDRIVE_FIND_FILE`. The [Slack tool contract](https://docs.composio.dev/toolkits/slack) explicitly describes non-idempotent posting. The [Drive toolkit](https://docs.composio.dev/toolkits/googledrive) allows duplicate folder names, so stored folder IDs and retry lookup are needed. [HubSpot](https://docs.composio.dev/toolkits/hubspot) exposes exact email filters and contact creation/update.

Delivery is **at least once**. A provider may have handled a call when its response times out, or when recording success fails. Slack can therefore repeat a message on retry; queue dedup prevents repeating an already-recorded success but cannot make the provider call exactly once. Drive/HubSpot lookup mitigates uncertain creates, without a cross-provider transaction or guarantee against concurrent external edits. The integrations UI states this consequence when retrying failed work.

## Routes, UI, and scheduling

- `GET /api/integrations/jobs` returns the newest 100 visible status records, without payloads, provider responses, lease tokens, or credentials; the response is private/no-store. An admin can inspect all recent jobs. Team members see only their own integration jobs for currently assigned clients. Optional `clientId` is authorized before listing.
- `POST /api/integrations/jobs` accepts a job ID and requeues only a visible failed/skipped job. The staff request policy requires `integrations.manage` for both methods. Team members cannot retry another actor's job or a job for an unassigned client. Execution rechecks original actor authority afterward.
- `POST /api/internal/integration-drain` uses the same configured `BOATSHIP_CRON_SECRET` and timing-safe comparison as existing internal job drains. It does not accept an ordinary browser session in place of the cron secret.
- The Integrations page shows queued/sending/complete/needs-connection/stopped states, attempt counts, safe error reasons, and refresh/retry controls. It refreshes active work once a minute while visible and stops when nothing is pending. Retrying records intent and, in production, starts a background drain after the response; the browser does not synchronously run provider actions.
- In production, `lib/queue-drain.ts` runs `drainIntegrationJobs` after any response that inserts or requeues jobs, and `drainWebhooks` after webhook dispatch and native form submission, using Next `after`. Leases keep concurrent drains safe. The hourly Worker cron awaits both drains through the routed application runtime as the retry path. `Promise.allSettled` lets both run even when one fails and makes the schedule fail visibly if either drain failed. Weekday product reminders remain on their existing cron.

Local `next dev` does not run the Worker cron automatically. Local and test enqueues do not start background drains. Hosted retry requires `BOATSHIP_CRON_SECRET`, the checked-in hourly trigger, valid per-user/server Composio configuration, and connected provider accounts. Slack also requires `COMPOSIO_SLACK_CHANNEL`; Drive parent placement uses the existing optional `COMPOSIO_DRIVE_PARENT_FOLDER_ID`. Apply the new migration before serving code that enqueues jobs. Queue retention/deletion and hosting alerts are not implemented by this change.

## Verification

`tests/integration-jobs.test.mjs` exercises stable provider-specific dedup, bounded backoff, provider-level false-success rejection, stable lifecycle markers, durable store recreation, duplicate enqueue preserving completion, concurrent claims, expired/stale leases, sibling independence, explicit retry, final-attempt crash recovery, and corrupt-file failure. These tests use temporary local files and synthetic provider results; they do not send messages, create folders, or change external contacts. Hosted credentials and real provider delivery still require an environment-specific release smoke test.

`npm run test:e2e` runs 14 behavioral tests against an isolated local PostgreSQL-compatible PGlite socket and an actual Next development server. It verifies migration backfill bytes and invalid-base64 transaction rollback, real cookie and bearer authorization, capability revocation, content/range/history responses, concurrent replacements and form submissions, engagement filtering and closed-write guards, queued HTTP status/retry permissions, and the actual relational queue helpers' deduplication, concurrent lease claims and final-attempt recovery. New queue date columns and future dates are checked under the fixture's non-UTC session. The test-only WASM hook is restricted to the generated Prisma query compiler; external provider configuration is cleared, and queue actors are denied before any provider execution. The suite rejects remote URL overrides and closes its own server, database, socket and bounded connection pool.
